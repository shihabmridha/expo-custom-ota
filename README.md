# expo-custom-ota

A self-hosted, multi-application OTA update server for Expo apps. Implements the
**Expo Updates v1 protocol**, so the stock `expo-updates` client talks to it with no
patches — you change a URL, not a library. Replaces EAS Update for teams that want to
host their own updates.

```
Developer                    expo-custom-ota                         Device
  expo export  ──▶  upload ──▶ validate, hash, sign  ──▶  signed manifest
                              store assets by SHA-256     immutable assets
```

- **Multiple applications**, each with its own update URL, channels, and signing key.
- **Channels** (`production`, `staging`, …) with promotion that re-points at the *same*
  signed bytes — what ships is what you tested.
- **Rollback** plus a `rollBackToEmbedded` kill-switch for updates already in the field.
- **Code signing** per application, with certificates generated by Expo's own library.
- **Content-addressed storage** with deduplication across releases and applications.
- **No build servers, no webhooks, no repository access** — you run `expo export` and upload.

## Quick start

Requires [Bun](https://bun.sh) 1.4+. Nothing else — SQLite and file storage are built in.

```bash
bun install
bun run db:migrate
bun run admin:create -- --email you@example.com --password 'a-long-password'
bun run dev            # API on :3000, dashboard on :5173
```

(The server also migrates automatically on every start; the explicit `db:migrate` only
exists so `admin:create` can run before the first boot.)

### Ship your first update

1. Open <http://localhost:5173>, log in, and **create an application**. A signing key is
   generated for it by default.
2. Copy the snippet from the application's **Client setup** tab into your Expo project's
   `app.json`, and save its certificate as `certs/certificate.pem`. Details and pitfalls:
   [docs/client-setup.md](docs/client-setup.md).
3. From your Expo project, publish:

   ```bash
   npm install --save-dev expo-custom-ota
   npx expo-custom-ota publish \
     --server http://localhost:3000 --app <application-uuid> --channel production \
     --email you@example.com --password 'a-long-password'
   ```

   See [packages/cli/README.md](packages/cli/README.md) for CLI installation and usage.
   Alternatively, `npx expo-custom-ota pack` + **Releases → Upload** in the dashboard does
   the same thing, and the **Simulator** tab shows exactly what a device would receive.

## Production

```bash
export OTA_PUBLIC_URL=https://ota.example.com
export SESSION_SECRET="$(bun -e 'console.log(crypto.randomUUID()+crypto.randomUUID())')"
docker compose up -d
docker compose exec backend bun run backend/scripts/create-admin.ts \
  --email you@example.com --password 'a-long-password'
```

Two things matter before your first publish, both covered in
[docs/deployment.md](docs/deployment.md):

- **`OTA_PUBLIC_URL` is forever.** It is baked into signed manifests; changing it later
  means republishing.
- **Back up the `/data` volume.** It holds the private signing keys — lose them and
  already-shipped binaries can never receive another update.

## Layout

```
backend/     Bun + Hono API
dashboard/   Vite + React admin SPA
packages/
  cli/         the expo-custom-ota CLI
  types/       shared types, no runtime code
  protocol/    Expo Updates v1 — pure, no HTTP/DB/filesystem
  contracts/   Zod schemas + route definitions, the single source of truth
  api-client/  typed fetch client derived from contracts
  api-sdk/     ergonomic wrapper used by the CLI and CI scripts
  db/          Drizzle schema, bun:sqlite client, migrations
```

## Status

Every flow is implemented and tested end-to-end over real HTTP, and Android over LAN passes
the full device checklist. **Verification against a production VPS and on iOS is still
outstanding** — see [device-verification.md](docs/device-verification.md). Until it passes,
treat this as pre-production.
